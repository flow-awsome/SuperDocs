# powerDocs — 다운로드형 AI 협업 개발 문서 하네스

개발팀(사람+AI)이 서비스를 컨설팅 → 설계 → 구현 → 검증 → 운영까지 끌고 가는 동안 쓰는 문서 체계를, 프로젝트마다 다시 설계하지 않고 **그대로 받아 적용**할 수 있게 만든 템플릿 저장소다. 이 저장소 자체는 어떤 서비스도 만들지 않는다 — 여기 담긴 것은 다른 프로젝트에 복사해 쓰는 두 종류의 도구다.

## 두 개의 최상위 폴더

| 폴더 | 언제 쓰는가 | 무엇인가 |
|---|---|---|
| [mastery](mastery/README.md) | 새 프로젝트 착수 시 **한 번** | 서비스 정체성/기술스택/이해관계자/성공기준을 묻는 인터뷰 툴킷. 답변을 종합해 "마스터 독스"(하네스 설정 계획)를 만든다 |
| [docs](docs/README.md) | 프로젝트가 진행되는 **내내** | 아키텍처·시나리오·계획·코드·테스트·히스토리·결정기록·트러블슈팅·투두·컨설팅·감사까지 갖춘 실제 운영 하네스 |

사용 흐름: **`mastery/`를 채운다 → 그 결과로 `docs/`를 설정한다 → 이후 개발은 `docs/`만 본다.**

## 왜 이렇게 나눴는가

처음엔 인터뷰용 질문지와 실제 운영 문서를 한 트리에 뒀는데, 그러면 "이게 초기 설정값을 위한 질문인지, 지금 프로젝트의 실제 상태인지"가 프로젝트가 진행될수록 헷갈린다. `mastery`는 정적인 설정 인터뷰, `docs`는 계속 갱신되는 살아있는 하네스로 물리적으로 분리했다.

## 설계 근거: 실제 실패 사례에서 배운 것

이 구조는 이론만으로 만들지 않았다. 실제로 8개월 넘게 진행 중인 엔터프라이즈 프로젝트의 문서 체계(총 500개 가까운 md 파일)를 조사한 결과, 이 하네스가 지향하는 것과 놀랍도록 비슷한 구조(아키텍처/계획/히스토리/트러블슈팅/컨설팅 분리, ADR, 페이즈 추적, 고객사별 분리)를 이미 자생적으로 채택하고 있었다는 것을 확인했다. 동시에 명확한 실패 지점도 발견했다:

- **"상태 문서"가 로그로 변질되는 문제**: 원래 "덮어쓰기가 정상"이라고 설계했던 상태 추적 문서가, 실제로는 세션마다 요약 문단을 위에 계속 추가하는 방식으로 운영되며 300줄이 넘는 벽이 되어 있었다. 실제 상태표에 도달하기도 전에 그 벽을 다 읽어야 하는 상태였다.
- **버전 전체를 스냅샷으로 얼리는 방식의 비용**: 구조 재편 시점마다 전체 문서 트리를 통째로 복제해 "읽기 전용"으로 얼려두는 방식이 문서량을 배로 늘렸다.
- **반면 잘 작동한 것**: 여러 관점이 같은 코드베이스를 교차로 감사하는 정기 감사 라운드, 위험도에 따라 착수 전 사용자 확인을 강제하는 게이트, 방향성 전용 요약 문서를 별도로 분리한 것.

이 하네스는 잘 작동한 패턴은 [docs/11-audit](docs/11-audit/README.md)(교차검증 감사)와 [docs/03-plan](docs/03-plan/README.md)의 위험도 게이트로 구조화하고, 실패한 패턴은 [docs/00-control-tower](docs/00-control-tower/README.md)의 명시적 규칙(덮어쓰기 vs append-only 구분, 크기 예산, 스냅샷 금지)으로 막도록 설계했다.

## 이 저장소를 실제 프로젝트에 쓰는 법

이 저장소는 GitHub 템플릿 저장소다. 새 프로젝트를 시작할 때마다 포크하지 말고 아래처럼 "Use this template"으로 독립된 새 저장소를 만든다 — 포크는 원본과 커밋 히스토리가 얽혀 있어서 원본 업데이트를 받아오려 할 때(PR/머지) 계속 충돌이 나지만, 템플릿으로 만든 저장소는 처음부터 히스토리가 분리된 완전한 새 저장소라 그런 문제가 없다.

1. 이 저장소 페이지 상단의 **[Use this template]** 버튼 → **Create a new repository**를 눌러 새 프로젝트 저장소를 만든다. (CLI로 할 경우: `gh repo create <새 저장소 이름> --template flow-awsome/SuperDocs --public --clone`)
2. 새로 만들어진 저장소를 클론해서 `mastery/README.md`부터 읽고 인터뷰를 진행한다.
3. `mastery/01-docs-blueprint/`에서 하네스 설정을 확정한다.
4. `docs/`를 실제 프로젝트 문서 루트로 쓰기 시작한다.

## 이 문서 체계 자체도 규칙이 아니다

모든 폴더의 README는 "왜 이렇게 나눴는지"를 설명하지만, 프로젝트 상황에 맞지 않으면 언제든 비판적으로 재검토하고 바꾼다. 다만 바꾸기로 한 판단은 [docs/07-decisions](docs/07-decisions/README.md)에 남긴다 — 그래야 다음 사람이 같은 논의를 반복하지 않는다.
