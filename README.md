# SuperDocs — 다운로드형 AI 협업 개발 문서 하네스

개발팀(사람+AI)이 서비스를 컨설팅 → 설계 → 구현 → 검증 → 운영까지 끌고 가는 동안 쓰는 문서 체계를, 프로젝트마다 다시 설계하지 않고 **그대로 받아 적용**할 수 있게 만든 템플릿 저장소다. 이 저장소 자체는 어떤 서비스도 만들지 않는다 — 여기 담긴 것은 다른 프로젝트에 복사해 쓰는 두 종류의 도구다.

## 두 개의 최상위 폴더

| 폴더 | 언제 쓰는가 | 무엇인가 |
|---|---|---|
| [mastery](mastery/README.md) | 새 프로젝트 착수 시 **한 번** | 서비스 정체성/기술스택/이해관계자/성공기준을 묻는 인터뷰 툴킷. 답변을 종합해 "마스터 독스"(하네스 설정 계획)를 만든다 |
| [docs](docs/README.md) | 프로젝트가 진행되는 **내내** | 아키텍처·시나리오·계획·코드·테스트·히스토리·결정기록·트러블슈팅·투두·컨설팅·감사까지 갖춘 실제 운영 하네스 |

사용 흐름: **`mastery/`를 채운다 → 그 결과로 `docs/`를 설정한다 → 이후 개발은 `docs/`만 본다.**

## 왜 이렇게 나눴는가

처음엔 인터뷰용 질문지와 실제 운영 문서를 한 트리에 뒀는데, 그러면 "이게 초기 설정값을 위한 질문인지, 지금 프로젝트의 실제 상태인지"가 프로젝트가 진행될수록 헷갈린다. `mastery`는 정적인 설정 인터뷰, `docs`는 계속 갱신되는 살아있는 하네스로 물리적으로 분리했다.

## 설계 근거: 실증 조사 결과

이 구조는 이론만으로 만들지 않았다. 8개월 이상 운영 중인 엔터프라이즈 프로젝트의 문서 체계(약 500개 md 파일)를 대상으로 사전 조사를 진행했고, 그 결과는 다음과 같다.

- 아키텍처·계획·히스토리·트러블슈팅·컨설팅의 분리, ADR, 페이즈 추적, 고객사별 분리 구조가 이 하네스가 지향하는 형태와 거의 동일하게 이미 자생적으로 채택되어 있었다. 이는 이 구조가 임의의 설계가 아니라 실제 운영 환경에서 반복적으로 수렴하는 패턴임을 뒷받침한다.
- 여러 관점이 같은 코드베이스를 교차로 감사하는 정기 감사 라운드, 위험도에 따라 착수 전 확인을 강제하는 게이트, 방향성 전용 요약 문서의 분리는 문서 신뢰도 유지에 유효한 것으로 확인됐다.
- 반면 "상태 문서"에 덮어쓰기 원칙 대신 세션마다 요약 문단을 계속 append하는 운영이 이어지면 300줄이 넘는 벽이 되어 실제 상태를 확인하는 비용을 키웠고, 구조 재편 시점마다 문서 트리 전체를 스냅샷으로 복제해 얼리는 방식은 문서량을 배로 늘렸다. 두 경우 모두 문서 체계의 규모 자체가 유지보수 부담으로 전환되는 지점이었다.

이 조사 결과에 따라, 유효성이 확인된 패턴은 [docs/11-audit](docs/11-audit/README.md)의 교차검증 감사와 [docs/03-plan](docs/03-plan/README.md)의 위험도 게이트로 구조화했고, 비용을 키우는 것으로 확인된 패턴은 [docs/00-control-tower](docs/00-control-tower/README.md)의 명시적 규칙(덮어쓰기 vs append-only 구분, 크기 예산, 스냅샷 금지)으로 원천 차단하도록 설계했다. 이 하네스를 그대로 적용하면 별도 시행착오 없이 조사로 검증된 구조를 바로 확보할 수 있다.

이 설계는 아래 외부 표준·공식 가이드와의 정합성을 검토해 근거를 보강했다: Anthropic의 공식 에이전트 하네스 가이드라인, 주요 AI 코딩 도구의 프로젝트 컨텍스트 관례, arc42·C4·4+1 아키텍처 표준, 결정 기록(ADR) 표준, 대규모 조직의 설계 합의 프로세스, 문서 분류 이론(Diátaxis), ISO 29119 테스트 표준, SRE 인시던트 대응 관행, AI 에이전트 컨텍스트 관리 원칙, 스펙 기반 개발 프레임워크. 검토 결과 기존 구조가 이들 표준과 대체로 정합함을 확인했으며, 확인된 구체적 격차는 관련 폴더에 반영했다. 전체 근거와 출처는 [docs/00-control-tower/external-reference-survey.md](docs/00-control-tower/external-reference-survey.md) 참조.

## 이 저장소를 실제 프로젝트에 쓰는 법

이 저장소는 GitHub 템플릿 저장소다. 새 프로젝트를 시작할 때마다 포크하지 말고 아래처럼 "Use this template"으로 독립된 새 저장소를 만든다 — 포크는 원본과 커밋 히스토리가 얽혀 있어서 원본 업데이트를 받아오려 할 때(PR/머지) 계속 충돌이 나지만, 템플릿으로 만든 저장소는 처음부터 히스토리가 분리된 완전한 새 저장소라 그런 문제가 없다.

1. 이 저장소 페이지 상단의 **[Use this template]** 버튼 → **Create a new repository**를 눌러 새 프로젝트 저장소를 만든다. (CLI로 할 경우: `gh repo create <새 저장소 이름> --template flow-awsome/SuperDocs --public --clone`)
2. 새로 만들어진 저장소를 클론해서 `mastery/README.md`부터 읽고 인터뷰를 진행한다.
3. `mastery/01-docs-blueprint/`에서 하네스 설정을 확정한다.
4. `docs/`를 실제 프로젝트 문서 루트로 쓰기 시작한다.
5. 저장소 루트에 `AGENTS.md`(또는 Claude Code라면 `CLAUDE.md`가 `@AGENTS.md`를 import)를 만들어 `docs/AGENTS.md`로 링크한다 — Cursor/Copilot/Windsurf 등 여러 AI 코딩 도구가 프로젝트 컨텍스트를 자동 인식하는 표준 위치는 루트이지, `docs/` 하위가 아니다 (근거: [docs/00-control-tower/external-reference-survey.md](docs/00-control-tower/external-reference-survey.md#ai-코딩-도구의-프로젝트-컨텍스트-관례)).

## 이 문서 체계 자체도 규칙이 아니다

모든 폴더의 README는 "왜 이렇게 나눴는지"를 설명하지만, 프로젝트 상황에 맞지 않으면 언제든 비판적으로 재검토하고 바꾼다. 다만 바꾸기로 한 판단은 [docs/07-decisions](docs/07-decisions/README.md)에 남긴다 — 그래야 다음 사람이 같은 논의를 반복하지 않는다.
