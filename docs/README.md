# docs/ — 운영 문서 하네스

하나의 서비스를 설계 → 구현 → 검증 → 운영까지 끌고 가는 동안, 개발자와 AI 에이전트가 같은 맥락을 공유하고 실수(디루전, 의도 이탈, 중복 작업, 토큰 낭비)를 최소화하기 위해 **실제 프로젝트 저장소에 복사해 쓰는** 문서 하네스다.

**이 하네스는 특정 조직 규모를 전제하지 않는다.** AI 하나가 혼자 개발을 진행하는 1인 프로젝트든, 여러 팀이 협업하는 엔터프라이즈 조직이든 — 목적은 같다: 지금 가용한 인력/에이전트가 몇이든, 그들이 프로젝트의 진짜 목적을 향해 방향을 잃지 않고 나아가게 하는 것. 폴더 구조와 문서 형식은 그대로 두고, 각 폴더의 "적용 강도"(예: [11-audit](11-audit/README.md)의 감사 렌즈 개수, [AGENTS.md](AGENTS.md) 5절의 담당 매핑)만 실제 가용 인력에 맞게 늘리거나 줄인다.

> 이 폴더는 처음부터 채워져 있지 않다. 프로젝트를 새로 시작한다면 먼저 저장소 루트의 [../mastery](../mastery/README.md)에서 최초 인터뷰를 마친 뒤 그 결과를 여기에 반영한다. 이미 인터뷰를 마쳤다면 [00-control-tower](00-control-tower/README.md)부터 읽는다.

## 이 하네스의 목적

1. **의도 보존** — 서비스의 핵심 의도와 기능이 시나리오·구조 설계에 맞게 진행되는지 항상 추적 가능하게 한다.
2. **디루전 방지** — AI가 맥락을 잃거나 잘못된 가정을 쌓아가지 않도록, 결정과 근거를 그때그때 기록한다.
3. **토큰 최적화** — 문서 자체가 AI에게 반복 학습시켜야 할 컨텍스트이므로, 구조화·압축·중복 제거를 통해 필요한 순간에 필요한 문서만 읽히도록 만든다.
4. **원활한 협업 통신** — 개발자·AI·팀원 간 의사결정, 질의응답, 진행상황이 한 곳에 모이도록 한다.
5. **CI/CD 및 유지보수까지 고려** — 완결성(엔터프라이즈 품질)과 비용 효율(운영 가능한 인프라 설계) 사이의 트레이드오프를 명시적으로 판단하고 기록한다.

## 이 문서는 규칙이 아니라 참고 자료다

이 하네스의 어떤 문서도 "절대 규칙"이 아니다. 개발팀(사람이든 AI든)은 이 문서를 참고하되, 상황에 맞지 않으면 비판적으로 검토하고 갱신해야 한다. 다만 **문서를 무시하기로 한 결정 자체는 [07-decisions](07-decisions/README.md)에 기록**한다 — 그래야 다음 세션의 AI나 다른 팀원이 같은 논의를 반복하지 않는다.

## 최종 판단 기준 (트레이드오프 저울)

이 하네스를 잘 쓰고 있는지 판단할 때 하나의 기준에 치우치지 않는다. 다음을 종합적으로 저울질한다:

- **목적 도달률** — AI를 사용했을 때 사용자의 실제 목적(기능 완성, 서비스 운영)에 얼마나 효과적으로 도달했는가.
- **구조적 완결성** — 엔터프라이즈급 완결성(테스트, 아키텍처, 결정기록)이 갖춰졌는가.
- **비용 효율** — 인프라·운영 비용이 프로젝트 규모에 맞게 산정되었는가 (과설계 금지).
- **토큰 효율** — 같은 정보를 더 적은 토큰으로 전달하고 있는가. 진행 경과에 대한 의미없는 중간보고는 스킵하고, [caveman](01-architecture/04-system-instructions/skill-usage-policy.md) 같은 압축 스킬을 상황에 맞게 활용한다.
- **CI/CD·유지보수 지속가능성** — 지금 당장이 아니라 6개월 뒤에도 이 구조로 협업이 가능한가.
- **사람이 검토 가능한 상태 유지** — 문서량이 늘어도 사람이 5분 안에 현재 상태를 파악할 수 있는가. (아래 "문서가 방대해질 때" 참조)

## 기본 기술 스택 (이 하네스의 기본값)

이 하네스는 아래 스택을 기본 전제로 설계되어 있다. 프로젝트마다 [../mastery/00-initial-intake](../mastery/00-initial-intake/README.md)에서 실제 스택을 재확인하고 편차를 기록한다.

- **언어**: TypeScript, Python
- **프레임워크**: NestJS (백엔드/TS), FastAPI (백엔드/Python), Next.js (프론트엔드/TS)
- **DB**: PostgreSQL (주 저장소), Redis (캐시/세션/큐)
- **인프라**: AWS — 완결성(가용성, 관측성, 보안)을 우선하되 비용 산정 기준을 항상 함께 명시

## 문서가 방대해질 때 (안티 블로트 원칙)

프로젝트가 길어지면 문서는 반드시 쌓인다. 그 자체는 문제가 아니다 — 문제는 사람이 "지금 상태"를 파악하기 위해 그 전체를 읽어야 하는 상황이다. 이를 막기 위한 3가지 장치:

1. **덮어쓰기 문서와 append-only 문서를 명확히 분리한다.** "상태"를 담는 문서(대시보드, 아키텍처 현황)는 항상 최신 상태로 덮어쓰고, "사실의 기록"을 담는 문서(히스토리, 결정기록, 감사 리포트)만 계속 쌓이게 한다. 이 규칙이 무너지면(상태 문서가 로그처럼 계속 append되면) 대시보드 자체가 읽을 수 없는 벽이 된다 — 정확히 이 실패를 겪은 실제 사례가 있어 [00-control-tower/doc-governance-policy.md](00-control-tower/doc-governance-policy.md)에 방지책을 명시해뒀다.
2. **append-only 문서는 개수가 아니라 "찾을 수 있는가"로 관리한다.** 개수 예산을 넘으면 삭제 대신 `archive/YYYY-MM/`로 이동하고 인덱스를 남긴다.
3. **정기적으로 여러 관점에서 전수조사한다.** [11-audit](11-audit/README.md)가 이 역할을 한다 — 일상적인 검증([05-test](05-test/README.md))이 놓치는 문서-코드 정합성, 기획의도 이탈 같은 문제를 잡아낸다.

자세한 폴더별 규칙은 [00-control-tower/doc-governance-policy.md](00-control-tower/doc-governance-policy.md) 참조.

## 파일/폴더 명명 규칙

- 폴더는 실행 순서를 나타내는 두 자리 숫자 접두어(`00-`, `01-`…)를 쓴다.
- 폴더/파일명은 영문 kebab-case로 통일한다 (경로 인코딩 문제, CI/CD 호환성, 검색 용이성 때문). 문서 **내용**은 한국어로 작성한다.
- 템플릿 파일은 `_template-*.md` 접두어를 붙여 실제 기록 파일과 구분한다.
- 실제 기록 파일은 날짜 또는 순번을 접두어로 붙인다: `2026-09-11-*.md`, `phase-01-*.md` 등.
