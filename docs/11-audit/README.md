# 11-audit — 전수조사 & 교차검증

일상적인 [05-test](../05-test/README.md) 검증은 "이 기능이 명세대로 동작하는가"를 확인한다. 이 폴더는 그보다 상위 레벨에서 **정기적으로, 여러 관점이 교차로** 전체 프로젝트를 훑어 문서-코드 정합성, 보안, 비즈니스 로직 누락, 기획 의도와의 괴리 같은 "일상 검증이 놓치는" 문제를 잡아내는 공식적인 사람 검토 의식(ritual)이다.

## 왜 "여러 관점 교차검증"인가

한 사람/한 관점이 전체를 감사하면 자신이 만든 맹점을 자신이 발견하지 못한다. 이 폴더는 서로 다른 렌즈(아키텍처, 보안, 비용, 테스트 무결성, 문서-코드 정합성 등)로 **같은 시점의 코드베이스를 독립적으로** 훑고, 그 결과를 교차 대조하는 구조를 강제한다. 이것은 팀이 여러 개 있어야만 가능한 게 아니다 — AI 하나, 개발자 한 명이라도 렌즈를 하나씩 바꿔가며 처음부터 다시 보면 같은 효과를 얻는다. 인력이 여러 명/여러 에이전트라면 렌즈를 나눠 맡아 동시에 진행할 수 있다는 차이뿐이다.

## 감사 라운드를 언제 여는가

- 큰 페이즈 종료 시 (다음 페이즈 진입 전 게이트)
- 프로덕션 첫 배포 전 (필수)
- 아키텍처를 크게 흔드는 변경 직후
- 오랫동안(예: 2개월 이상) 전체 감사가 없었을 때 — [00-control-tower/project-dashboard.md](../00-control-tower/project-dashboard.md)의 "다음 감사 예정일"로 추적

## 핵심 규칙 — "고쳤다고 끝난 게 아니다"

발견된 문제를 그 자리에서 고쳐도, **다음 감사 라운드가 실제로 재확인하기 전까지는 "닫힘"으로 간주하지 않는다.** 스스로 "고쳤음"이라고 선언한 항목이 실제로는 재발하거나 다른 곳에서 회귀를 일으키는 경우가 실무에서 반복적으로 발생하기 때문이다. [02-audit-closure-log](02-audit-closure-log/README.md)가 이 재검증 고리를 강제한다.

## 사람의 역할

- 감사 결과(특히 🔴)는 AI가 임의로 "괜찮다"고 넘기지 않는다 — [00-control-tower/open-questions.md](../00-control-tower/open-questions.md)에 올리거나 사용자에게 직접 확인한다.
- 감사 리포트는 사람이 읽고 의견을 남기는 것을 전제로 작성한다 — 발견 사항 하나당 근거(파일:라인 또는 문서 링크)를 반드시 포함해 사람이 직접 검증할 수 있게 한다.
