# 07-decisions — 결정기록 (ADR)

"왜 그렇게 하기로 했는가"의 판단과 근거를 기록한다. 로직별/아키텍처별/진행상황별로 폴더를 나눠, 나중에 비슷한 결정을 검색할 때 범위를 좁힐 수 있게 한다.

## 작성 원칙 (ADR 공통)

- 모든 결정 기록은 동일한 형식을 따른다: 배경 → **결정 동인** → 고려한 옵션 → 선택과 이유 → 트레이드오프 → 재검토 조건. "결정 동인"은 이 결정에서 무엇을 최우선으로 볼지(비용/일정/보안/확장성 등)를 옵션 비교보다 먼저 명시해, 왜 그 옵션을 골랐는지가 나중에도 재구성 가능하게 한다 (MADR 관행).
- **ADR 1건 = 결정 1개.** 여러 결정을 한 ADR에 묶지 않는다 — 나중에 그중 하나만 뒤집혔을 때 나머지까지 같이 대체 처리해야 하는 문제가 생긴다. 템플릿 하단의 체크박스로 이를 확인한다.
- 결정은 **불변 기록**이다. 나중에 결정이 뒤집혀도 기존 문서를 지우지 않고, 새 결정 문서를 만들어 이전 문서에서 링크한다 (`→ 이 결정은 [ADR-0012]에 의해 대체됨`).
- 사소한 기술적 선택까지 전부 기록하지 않는다 — **되돌리기 비용이 크거나, 다시 논의될 가능성이 있는 결정**만 남긴다. 기준: [01-architecture/04-system-instructions/agent-operating-rules.md](../01-architecture/04-system-instructions/agent-operating-rules.md) 7절의 위험도(Lv)가 6 이상이면 예외 없이 남긴다.

## 대체(Superseded) vs 재해석(Reinterpreted)

결정이 뒤집히는 방식은 하나가 아니다. 구분하지 않으면 "결론은 안 바뀌었는데 왜 새 ADR이 필요한지" 헷갈리게 된다.

| 상황 | 처리 |
|---|---|
| 결정 자체가 틀렸거나 상황이 바뀌어 다른 선택을 한다 | 새 ADR 작성, 기존 문서에 `대체됨 (→ ADR-XXXX)` 표시 |
| 결정은 여전히 맞지만, 그 결정이 실제로 무슨 뜻이었는지에 대한 해석이 새로운 상황에서 달라진다 (예: "이메일 기반 인증"이라는 결정이 이메일이 없는 사용자층에도 적용되는지 재검토) | 기존 ADR을 대체 처리하지 않는다 — 새 ADR을 만들되 상태를 `제안됨`/`확정`으로 쓰고, 배경 절에 "ADR-XXXX의 재해석: (원래 결정) 자체는 유지, (구체적으로 무엇을) 이번에 명확히 함"이라고 적는다. 원래 ADR에는 `→ ADR-YYYY에서 재해석됨` 링크만 추가한다 (대체 표시는 하지 않는다). |

재해석이 필요해지는 시점은 대개 새 고객/새 세그먼트 요구사항을 받았을 때다 — [12-customers](../12-customers/README.md)의 충돌로그에서 "baseline 자체를 개선"으로 처리 결과가 나오면 이 재해석 절차를 거친다.

## 파일명 규칙

`ADR-<4자리번호>-<슬러그>.md` (번호는 전체 07-decisions 하위에서 전역 일련번호). 여러 에이전트/기여자가 동시에 ADR을 작성해 번호가 충돌할 위험이 있으면(예: 병렬 세션), 번호를 예약하지 말고 커밋 직전에 마지막 번호를 다시 확인해 채번한다 — log4brains류 도구는 이 문제를 날짜 접두(`YYYYMMDD-`) 파일명으로 피한다는 점도 참고.
