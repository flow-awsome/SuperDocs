# 이해관계자 및 의사결정 권한

## 1. 이해관계자 맵

> 혼자(또는 AI 단독으로) 진행한다면 이 표는 채우지 않고 "본인이 아래 역할을 전부 겸함"이라고만 적고 다음 절로 넘어간다. 아래 행은 인력이 여러 명일 때의 예시일 뿐, 필수 항목이 아니다.

| 역할 | 이름/팀 | 관심사 | 의사결정 권한 범위 |
|---|---|---|---|
| 프로젝트 오너 | | 전체 방향/예산 | 최종 승인권 |
| 아키텍처 리드 | | 기술 구조 | 아키텍처 결정 |
| PM/PMO | | 일정/스코프 | 페이즈 스코프 조정 |
| QA 리드 | | 품질 기준 | 검증 통과 기준 |
| (추가) | | | |

## 2. 의사결정 에스컬레이션 경로

- AI/개발팀이 판단할 수 없는 사안이 생기면 누구에게 확인하는가?
- 긴급도별 응답 기대 시간은? (즉시 / 당일 / 페이즈 종료 전)
- 사용자가 자리를 비울 때의 기본 판단 원칙은? (예: 보수적으로 진행, 혹은 [docs/09-todo](../../docs/09-todo/README.md)에 대기 큐로 남기고 다음 가능한 작업으로 전환)

## 3. 범위 경계 (Scope Boundary)

- 이 프로젝트가 다른 시스템/팀과 맞닿는 지점은 어디인가? (외부 API, 다른 서비스와의 계약) — 그 상대가 **별도 Git 저장소**라면 여기서 개략만 적고 [05-related-projects.md](05-related-projects.md)에서 저장소 단위로 구체화한다.
- 이 하네스가 관리하는 범위와 관리하지 않는 범위 (예: 디자인 시스템은 별도 저장소에서 관리)

이 문서의 결론은 [docs/01-architecture/03-system-definition/non-goals-and-boundaries.md](../../docs/01-architecture/03-system-definition/non-goals-and-boundaries.md)에도 반영한다.
